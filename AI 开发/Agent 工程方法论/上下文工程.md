核心观点：避免 Context 的过度工程化，简化架构比增加复杂层更有效。Manus 自 3 月发布以来已重构 5 次。

Manus 三大核心策略：缩减（Reduction）→ 隔离（Isolation）→ 卸载（Offloading），三者相互支撑。

### 上下文缩减策略

上下文持续增长导致「上下文腐烂」（Context Rot）：推理变慢、质量下降、无意义重复。大多数模型在 12.8 万\~20 万 Token 时性能开始下降，远低于硬件极限。

#### Cursor：万物皆可文件化

用文件作为基础单元，将冗长的工具结果、终端会话、聊天记录全部转化为文件，让 Agent 在需要时自己去找。

- 工具结果写入文件：Shell/MCP 返回的巨大 JSON 写入 `output.log`，上下文中只保留文件引用，Agent 用 `tail`/`grep` 按需查看。
- 总结阶段引用历史：触发总结时，Agent 拿到摘要 + 指向历史记录文件的引用，可搜索找回细节。
- 终端会话同步文件：集成终端的所有输出同步到本地文件系统，Agent 可用 `grep` 在日志中搜索错误行。
- 实测效果：MCP 工具调用任务的 Token 总消耗降低 46.9%。

#### Manus：结构化可逆缩减

设计为有明确触发机制、分阶段执行的结构化流程。

- 腐烂前阈值（Pre-rot Threshold）：通过评估识别性能下降点（通常 12.8 万\~20 万 Token），作为触发条件。
- 工具结果双版本机制：每个工具调用维护完整版（原始内容存文件系统）和紧凑版（只存引用如文件路径）。对「陈旧」结果用紧凑版替换完整版，保留较新结果的完整版指导下一步决策。
- 第一步：紧凑化（Compaction）：无损、可逆。剥离可从外部状态重建的信息（如文件写入后只保留 path，content 外部化）。通常只用于最早的 50% 历史记录。
- 第二步：摘要化（Summarization）：有损、带保险。执行前将完整上下文转储到日志文件，创建快照存档。使用完整版本（非紧凑版本）生成摘要，保留最后几次完整工具调用保持连贯性。
  - 当压缩达到收益递减点时触发（继续逐条压缩的边际收益开始下降）。
  - 关键技巧：避免 free-form 格式，采用结构化 Schema。预定义摘要的 Schema/表格结构，让 AI 直接往格式里填充，确保完整性和一致性。

### 工具空间设计

工具过多会导致上下文混淆（调错工具、幻觉不存在的工具）和 Token 浪费。

#### Cursor：工具说明书文件化

- 索引层：System Prompt 只包含工具名称列表。
- 发现层：详细描述、参数定义同步到本地文件夹，Agent 用 `grep` 或语义搜索按需拉取。
- 额外收益：工具状态（如 MCP 服务器需重新认证）可通过文件传达给 Agent。

#### Manus：分层行动空间

认为对工具描述做动态 RAG 不可行（会干掉 KV 缓存，旧调用记录成为陷阱）。

- L1 原子函数调用：极少数固定正交的原子函数（读写文件、执行 shell、搜索），对 KV 缓存友好。
- L2 沙盒工具：格式转换器、语音识别等预装在 Linux 虚拟机沙箱中，Agent 通过 L1 的 shell 命令动态交互（`ls /bin`、`mcp_cli --help`）。
- L3 软件包与 API：允许 Agent 编写 Python 脚本处理大量计算或复杂第三方服务，只返回摘要结果。

### 多 Agent 协作模式

#### 架构组件

- 规划器（Planner）：分配任务。
- 知识管理器（Knowledge Manager）：审查对话，决定什么应保存到文件系统。
- 执行器子 Agent（Executor）：执行规划器分配的任务。

#### 任务委托模式（通过通信实现隔离）

主 Agent 发任务，子 Agent 交结果，中间过程免打扰。适用于「过程不重要，只关心结果」的任务。Manus 内部称为「Agent 即工具」。

#### 信息同步模式（通过共享上下文实现协作）

子 Agent 创建时能看到主 Agent 完整的先前上下文，但拥有独立的系统提示词和行动空间。适用于高度依赖历史信息的综合分析任务。成本较高（Prefill 大输入 + 无法复用 KV 缓存）。

#### 踩坑教训

- Manus 最初用 `todo.md` 做任务规划，约 1/3 的动作都在更新待办列表，浪费 Token。改用专门的规划器 Agent 后解决。
- 避免拟人化分工：人类因认知限制按角色组织，但 LLM 不一定有这些限制。子 Agent 的核心目标是隔离上下文，而非模拟人类分工。

#### 结构化输出契约

- 共享沙箱：同一会话共享文件系统，通过文件路径传递信息。
- 输出 Schema：主 Agent 定义强制执行的 API 合同。
- 约束解码：`submit_result` 工具强制结果符合 Schema。

### 设计哲学

- Cursor「少即是多」：最初提供给模型的细节越少，效果越好，让 Agent 自行抓取相关上下文。
- Manus「少构建，多理解」：每次简化架构，系统都变得更快、更稳定、更智能。上下文工程的目标是让模型的工作变得更简单。
- 共同方向：从「如何把更多信息塞进上下文」变成「怎么给 Agent 创建信息丰富、易于探索的外部环境」。
- Bitter Lesson（苦涩的教训）：保持简单和无偏见的设计，更容易适应模型改进。接受持续变化，避免限制性框架。
- 验证方法：在不同强度的模型上运行 Agent 评估，如果性能没有随更强模型提升，说明框架正在拖累 Agent。

### 模型路由策略

Manus 采用任务级路由，不同任务使用不同模型：

| 任务类型  | 推荐模型   |
| ----- | ------ |
| 编码    | Claude |
| 多模态任务 | Gemini |
| 数学和推理 | OpenAI |

同时利用 KV Cache 优化成本和延迟。

### 评测体系

Manus 最初使用公开评测集（如 GAIA），但发现与实际用户行为和预期偏差很大。现在采用三层评测体系：

| 评测方式      | 说明                                     | 适用场景      |
| --------- | -------------------------------------- | --------- |
| 黄金标准：用户评分 | 每次任务结束后让用户评分，计算完成任务的平均用户得分             | 真实用户满意度   |
| 内部自动化测试   | 自建评测集（公开评测集偏 read-only + 自设计的执行/事务性任务） | 回归测试、架构验证 |
| 实习生人工评测   | 网站生成、数据可视化等难以量化的任务，依赖主观人工评测            | 创意/生成类输出  |
